# Knoa 产品体验与能力产品化完整计划

> 状态：执行计划
> 更新：2026-08-21
> 目标：把 Knoa 从“能力完整的本地 Agent Platform”推进为“普通用户可以稳定完成真实工作的个人电脑助手”。

## 1. 结论与产品目标

Knoa 已经具备真实执行闭环，而不是聊天 Demo：

- Node 可以访问本机文件、Shell 和桌面能力；
- Agent 可以调用模型、Tool、MCP、Skill 和 Codex Runtime；
- Conversation、Task、Execution、Approval、Artifact 和通知都可以持久化；
- App、CLI、TUI 和 Feishu 使用同一个 Core；
- Hub、Node、Workspace、Relay、P2P 和 mDNS 已形成跨设备基础设施。

当前主要问题不是“功能太少”，而是：

1. 首次使用路径过长；
2. 技术概念暴露给了普通用户；
3. 连接、配置和更新失败时恢复成本高；
4. 有能力但没有足够多的任务模板和成功示例；
5. 多渠道和多模态能力还没有达到一致、稳定的产品体验。

产品北极星：

> 用户连接一台电脑后，在 5 分钟内完成一个真实工作，并且知道工作是否成功、失败后如何恢复。

## 2. 产品定位

### 2.1 核心定位

Knoa 是一个 local-first 的个人电脑 Agent：

- App 负责输入、状态、审批和结果查看；
- Node 负责本地执行、数据和运行时；
- Hub 负责身份、Workspace、Node 目录和跨设备协调；
- Agent 负责决定如何完成目标；
- Capability Gateway 负责权限、审批、审计和幂等。

### 2.2 首要用户

#### A. 技术型个人用户

需要让 Agent 操作本机、处理代码、运行测试、查看服务和维护项目。

#### B. 工程团队成员

需要连接 GitLab、Jira、MCP 和后台任务，持续处理研发与运维工作。

#### C. 业务知识工作者

需要整理文件、分析图片、搜集资料、生成报告和设置周期性工作。

### 2.3 暂不作为首要目标的用户

- 不愿安装本地 Node 的纯聊天用户；
- 需要复杂企业权限和审计的组织管理员；
- 需要完全无人值守高风险操作的用户。

这些方向可以保留，但不应阻塞个人电脑助手主线。

## 3. 当前能力边界

### 3.1 已具备生产价值的能力

| 能力 | 可以解决的问题 | 使用前提 |
|---|---|---|
| 本机文件 | 读取、整理、写入、转换文件 | Node 有对应目录权限 |
| Shell 与桌面 | 执行命令、查看窗口、截图、键鼠操作 | 本机权限和 Tool Policy 允许 |
| 工程研发 | 分析代码、修改代码、运行测试、接入 Codex | Codex Runtime 和工作目录可用 |
| Web 研究 | 搜索、抓取、汇总网页 | Web Tool/MCP 已启用 |
| 图片与文件 | 图片理解、Artifact 上传、保存、分享 | 视觉模型和文件权限可用 |
| 后台任务 | 一次性、定时、周期、事件触发任务 | Task 和通知配置可用 |
| 审批治理 | 高风险操作确认、暂停、恢复、审计 | Approval Channel 可达 |
| MCP 业务系统 | Jira、GitLab 等业务数据和动作 | MCP Server、凭据和授权已配置 |
| 多渠道 | App、CLI、TUI、Feishu | 对应客户端/凭据已配置 |

### 3.2 当前不能承诺为“开箱即用”的能力

- DingTalk Channel 尚未完成；
- mDNS 在所有 Windows 网络环境中稳定发现尚未达到产品级保证；
- P2P、Relay、mDNS 的切换仍有用户可感知异常；
- llama.cpp 视觉模型首次请求偶发空 observation；
- Codex 的直接使用和 Agent 委派语义仍不够自然；
- 多人协作、组织级策略和成本管理尚未完整；
- Web、桌面和移动端的诊断能力不完全一致。

## 4. 用户体验原则

1. 用户目标优先于内部对象。
2. 默认隐藏 mDNS、ICE、DataChannel、revision、generation 等实现细节。
3. 所有异步操作都必须有局部进度、可取消、可重试和最终状态。
4. 失败必须说明“发生了什么、是否产生副作用、下一步怎么做”。
5. 配置只有一个发布入口；App、Node Console、CLI 和 YAML 使用同一校验链。
6. 连接方式自动选择，用户默认只看到“本地连接、远程连接、正在修复”。
7. 危险动作默认 fail-closed，但不能让用户不知道为什么被阻止。
8. 新用户不需要先理解 Workspace、Node、Agent、Model 的内部边界。
9. 每一个主要功能都必须有一个可复制的真实任务示例。
10. 运行中的工作不能因为页面切换、网络切换或短暂重连而丢失。

## 5. 核心用户旅程

### 5.1 首次连接电脑

目标：用户不超过 5 分钟完成 App 与 Node 连接。

```text
安装 Node
  -> 打开 Node Console
  -> 一键检查 Node 健康
  -> 生成一次性配对码
  -> App 扫描
  -> 自动发现/验证本地连接
  -> 显示“已连接，可以开始工作”
```

验收标准：

- 普通用户不需要区分 Enrollment 和 Pairing；
- QR 过期时可以一键重新生成；
- 相机权限拒绝时有明确恢复动作；
- Node 离线时不出现永久 loading；
- 配对完成后直接进入“开始工作”页面；
- 首次连接成功率不低于 90%。

### 5.2 第一次完成真实工作

首屏提供 6 个任务入口：

- 分析一个本地文件；
- 分析一张截图；
- 修复一个代码测试；
- 整理一个文件夹；
- 创建一个每天执行的任务；
- 连接 Jira/GitLab 并查看工作项。

每个入口都提供：示例输入、权限说明、预计动作、成功结果和失败恢复。

### 5.3 新建会话

当前会话只需要展示：

- 当前 Node；
- 当前可直接使用的 Agent；
- 当前连接状态；
- 输入框、附件、语音和发送。

Agent 配置内部应拆成两个独立能力：

```text
允许用户直接使用：是/否
允许其他 Agent 委派：是/否
```

不要让用户理解 `visibility=user/delegate/system` 的内部枚举。

### 5.4 长任务与后台任务

用户只需要选择：

- 现在执行；
- 指定时间；
- 每天；
- 每周；
- 固定间隔；
- 由业务事件触发。

Cron、时区、事件来源和并发限制进入高级设置。

创建前显示自然语言摘要：

> 每天 18:30（北京时间）检查 GitLab 失败 Pipeline，发现失败后通知我。

### 5.5 失败恢复

所有失败页面统一展示：

```text
发生了什么
当前是否已经执行过动作
系统是否正在自动恢复
下一步建议
重试 / 编辑后重发 / 查看诊断 / 返回工作区
```

## 6. P0 计划：稳定完成工作

P0 的目标是减少“看起来能用但用户不敢依赖”的情况。

### P0-1 统一连接状态和优先级

#### 产品改动

- 默认隐藏 mDNS、P2P、Relay 的技术名称；
- 展示“本地网络”“安全远程连接”“正在自动修复”；
- 高级诊断中显示具体链路；
- 明确当前请求是否已经切换链路；
- 断链时所有请求同时启动可用路径；
- mDNS 成功后允许无感切换到更高优先级链路；
- 低优先级请求完成后再切换，避免直接打断业务。

#### 技术要求

- 统一记录发现、健康检查、认证、请求承载四个阶段；
- Node 和 App 使用同一个 Transport Health 状态模型；
- 增加 mDNS discovery success rate、health verification rate、switch latency；
- 断链后按 `mDNS > p2p > relay` 选择可用链路；
- 每次请求携带同一业务 request id，避免重试造成重复动作。

#### 验收

- 用户不需要手动选择传输方式；
- 链路切换不丢会话、不重复副作用；
- 支持链路切换的请求成功率不低于 99%；
- Node Console 能区分“未广播、未发现、健康检查失败、认证失败、请求失败”。

### P0-2 Node 一键健康诊断

Node Console 增加“检查 Node”按钮，依次检查：

- Node 进程；
- Core 端口；
- Gateway 端口；
- Hub/Relay；
- mDNS 广播；
- App 局域网发现；
- P2P ICE；
- Codex Runtime；
- llama.cpp；
- 视觉模型；
- 配置校验；
- 工作目录和权限；
- 磁盘空间。

结果分为：

- 正常；
- 可用但存在风险；
- 需要处理；
- 无法检查。

每一项都提供复制诊断和建议动作。

### P0-3 Windows 服务和更新自愈

- 停止时清理整个 Node 子进程树；
- 启动失败时显示真实原因，不显示空白重试循环；
- 端口被占用时显示占用 PID 和处理建议；
- 更新前自动备份当前版本和配置；
- 更新后执行健康检查；
- 健康检查失败自动回滚；
- 重启页面显示停止、启动、检查、完成四个阶段；
- 日志中区分旧进程、新进程和孤儿进程。

### P0-4 图片输入稳定性

- 发送前预检图片模型是否可用；
- 对视觉模型做连接和能力预热；
- 对“空 observation”做一次受控自动重试；
- 重试不重复上传、不重复创建业务动作；
- 向用户展示“图片已上传，视觉分析正在重试”；
- 连续失败时提供切换视觉模型和查看 Node 诊断入口；
- 记录模型、耗时、图像尺寸、失败原因和重试结果。

### P0-5 Agent 可用性语义

- 拆分“用户直接使用”和“允许被委派”；
- Agent 列表显示安装状态、启用状态和不可用原因；
- Codex 提供“检查 Runtime”动作；
- 新会话只显示可直接使用且健康的 Agent；
- 被隐藏的 Agent 提供“为什么不可见”说明；
- 修改 Agent 能力时显示影响范围和是否需要重启。

## 7. P1 计划：效率和能力产品化

### P1-1 任务模板中心

首批模板：

- 每日检查 GitLab Pipeline；
- 每日汇总 Jira 待办；
- 每周整理指定文件夹；
- 监控本地服务；
- 每日生成工作摘要；
- 定时分析指定目录中的新图片/PDF；
- 发现事件后等待审批再执行。

模板必须包含：

- 目标说明；
- 所需连接；
- 所需权限；
- 预计运行时间；
- 结果样例；
- 失败处理方式；
- 通知渠道。

### P1-2 结果交付中心

用户可以统一查看：

- 最终答案；
- 生成的文件；
- 图片和 Artifact；
- 执行摘要；
- 使用了哪些工具；
- 哪些动作需要审批；
- 下一步建议。

增加：

- 一键保存；
- 一键分享；
- 一键导出 Markdown/PDF/JSON；
- 结果搜索；
- 按任务、Node、Agent、时间过滤。

### P1-3 MCP 和业务连接向导

用户不应从空白配置开始填写 MCP。

向导流程：

```text
选择业务系统
  -> 登录/填写连接信息
  -> 检查权限
  -> 展示可用能力
  -> 用户选择允许的操作
  -> 保存并测试
  -> 提供一个真实示例任务
```

首批重点：Jira、GitLab、飞书、钉钉。

### P1-4 DingTalk Channel

目标不是简单接收 Webhook，而是实现与 Feishu 的语义一致：

- 文本会话；
- 图片和文件；
- Task 状态；
- Approval 卡片；
- 失败重试；
- 用户身份绑定；
- 会话映射；
- 多语言和权限策略。

优先使用官方 Stream 长连接模式，避免要求公网回调地址。

### P1-5 App 信息架构简化

默认导航只保留：

- 工作区；
- 当前 Node；
- 会话；
- 任务；
- 设置。

Node、Workspace、Account 的边界继续保留，但普通用户路径不主动展示所有层级。

- Context Window；

### 8.3 Agent

Agent 编辑器默认只显示：

- 名称；
- 用途；
- 模型；
- 是否可直接使用；
- 是否允许委派；
- 是否为默认 Agent；
- 是否健康。

Tools、Capability、Runtime 限制和 Delegation Budget 放入高级设置。

### 8.4 系统

系统页面负责：

- 更新；
- 重启；
- 服务状态；
- 诊断报告；
- 日志摘要；
- 备份和恢复；
- 高级 JSON。

高级 JSON 必须明确标注：

> 仅用于审计和紧急维护，日常修改请使用可视化页面。

## 12. 验收策略

### 12.1 三条黄金路径

每个版本必须真机验证：

1. Android App → Windows Node → 本地文件处理；
2. Android App → Windows Node → 图片输入 → llama.cpp 视觉模型；
3. Android App → Hub → Relay/P2P/mDNS → Codex 会话。

### 12.2 每次发布必须验证

- 冷启动；
- 重新配对；
- Node 重启；
- App 断网后恢复；
- Node 端口占用；
- mDNS 广播和发现；
- P2P 失败转 Relay；
- Relay 失败转本地连接；
- 图片第一次请求；
- 文件上传和下载；
- Task 中途重启；
- Approval 只提交一次；
- Codex 直接使用；
- Feishu 消息和文件；
- Windows 更新后回滚。

### 12.3 发布门禁

任何以下问题都阻止正式发布：

- Node 进程启动失败但 UI 显示成功；
- 用户无法判断业务动作是否已经执行；
- 连接重试可能重复副作用；
- 图片、文件或审批卡片状态丢失；
- 默认配置无法通过校验；
- 新版本更新后端口未恢复；
- Agent 出现在列表中但无法启动；
- 关键错误只有“请重试”而没有恢复动作。

## 13. 90 天执行节奏

### 第 1-2 周：可靠性基线

- 统一连接状态模型；
- 增加 Node 健康诊断接口；
- 修复 Windows 重启和更新状态；
- 修复视觉模型空 observation 自动重试；
- 增加 Codex Runtime 检查；
- 建立黄金路径真机测试。

### 第 3-4 周：新用户和会话体验

- 首次连接向导；
- 任务模板入口；
- Agent 可用性说明；
- 简化新会话 Agent 选择；

## 14. 版本完成定义

本计划第一阶段完成的标准不是“页面更多”，而是：

1. 新用户能在 5 分钟内连接 Node；
2. 用户能在首页直接找到真实任务入口；
3. Codex、Knoa 和自定义 Agent 的用途清晰；
4. mDNS、P2P、Relay 自动选择且不打断业务；
5. 图片、文件、审批和长任务失败后可以恢复；
6. Windows Node 更新、停止、启动、回滚可观察；
7. Node Console 能自己定位大多数问题；
8. App、Feishu、DingTalk 对同一任务的状态一致；
9. 每个核心功能都有成功示例和可复制模板；
10. 用户不需要读日志或编辑 JSON 才能完成常规工作。

## 15. 最终产品原则

Knoa 不应该把“我有很多 Tool”作为主要卖点，而应该让用户感受到：

> 我把一件真实工作交给它，它能在我的电脑上安全地完成，并且我始终知道进展、结果和下一步。

后续所有功能、界面和基础设施优化，都应以这个用户承诺为验收标准。
