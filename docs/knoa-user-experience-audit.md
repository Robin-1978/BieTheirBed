# 小诺用户体验全盘审查

> 日期：2026-08-10
> 范围：Android App、Secure Gateway 与 Core 的用户可见闭环
> 原则：项目处于正向开发阶段，直接建立正确模型，不保留错误的旧产品语义。

> 实施状态：本文件记录的是重构前问题基线。2026-08-10 已按
> [产品正向实施计划](./knoa-product-forward-implementation-plan.md) 完成 P0/P1/P2 代码闭环；
> 每项落地证据和发布前验证见实施计划第 12 节。

## 1. 总体结论

当前 App 已具备安全配对、持久对话、后台执行、权限确认、附件、推送和私有更新的
基础能力，但多个页面仍直接映射内部实现，缺少用户可以理解和恢复的完整闭环。

本轮不做“旧 Task 外面再包一层”的兼容设计。领域模型直接调整为：

```text
Task
  ├── 目标、附件、启动方式、启用状态、通知方式
  └── TaskExecution[]
        └── ExecutionAttempt[] 仅内部可见
```

界面只出现“任务”和“执行记录”。Schedule、Trigger、Run、Attempt 不进入产品文案。

## 2. P0：必须先解决

### 2.1 任务与执行记录混为一体

- 当前任务列表实际逐条展示执行聚合；
- `attempt_count` 被错误显示为“执行次数”；
- 定时与事件启动的定义没有进入 App；
- “重新执行”创建新记录后仍停留在旧详情，并在列表产生重复任务。

目标：Task 是稳定可编辑的定义；TaskExecution 是不可编辑的历史快照。任务详情展示
启动方式和执行记录，执行详情负责结果、产物、审批与运行控制。

### 2.2 重新配对可能继承旧连接状态

- 设备、会话 Token、Core Session 和事件游标分别使用全局固定键；
- 配对新 Gateway 时没有原子清理旧 Session 与事件游标；
- 新设备可能尝试读取旧 Core Session，或从旧 Gateway 的高事件序号继续订阅，造成
  页面报错或漏掉通知。

目标：连接身份作为一个原子账户记录保存。Gateway 或 device 变化时同步清理认证会话、
Core Session、事件游标和更新断点；提供“重新配对/移除此设备”的用户入口。

### 2.3 对话执行缺少控制和失败恢复

- 后端已有取消 ChatTurn 能力，界面没有“停止生成”；
- 失败或取消后没有重试、编辑后重发；
- 流断开并达到重试上限后只显示一条可关闭错误，没有针对该回复的恢复按钮；
- 用户阅读旧消息时，内容变化会强制滚动到底部。

目标：运行中的回复显示“停止”；失败卡片显示“重试”和“复制到输入框”；仅当用户原本
位于底部时自动跟随新内容。

### 2.4 错误状态经常不可恢复

- 多个页面的异步加载没有 `catch`，失败后永久显示加载动画；
- `GatewayError` 直接暴露 `invalid_request`、`http_503` 等内部代码；
- 拍照、录音、转写、审批等错误有的完全没有可见反馈。

目标：统一用户错误模型，至少区分连接中断、权限不足、服务忙、输入无效和操作冲突；
所有加载页必须有错误说明和重试按钮。

### 2.5 强制更新策略没有真正生效

- App 能识别 `min_supported_version_code`，但只在版本页显示红字；
- 过旧版本仍可继续进入对话、创建任务和执行高风险操作。

目标：启动后发现强制更新时进入受限模式，只保留更新、连接诊断和退出能力；下载完成后
即使 App 重启也能继续安装，不要求重新下载。

## 3. P1：核心闭环问题

### 3.1 会话历史不可访问

“新话题”会创建新 Session，但 App 没有历史会话入口。用户无法返回旧对话，也无法在
切换前确认未发送文字、附件或录音。

目标：提供历史会话列表；存在草稿时切换话题需要保留草稿或明确确认。

### 3.2 附件缺少逐项状态

- 多附件整体并行上传，没有单项进度、失败原因和精确重试；
- 点击整张待发送附件卡片即删除，容易误触；
- 接收图片默认只进 App 缓存，“保存/分享”并不等于明确保存到相册；
- 任务结果附件仍只打开系统分享面板，没有与对话一致的图片预览。

目标：附件逐项显示准备、上传、失败和重试；删除使用独立按钮；图片明确区分“缓存预览”、
“保存到相册”和“分享”。对话与任务共用同一 Artifact 组件。

### 3.3 权限确认信息不足

- 卡片主要展示工具名和后端 reason，用户不知道将影响什么对象、是否可撤销；
- 操作失败没有错误反馈；
- 任务详情通过事件顺序推断待确认，多个审批时可能被不相关的解决事件清空。

目标：审批展示动作、影响范围、风险、可撤销性和关键参数；直接使用持久 Approval 状态，
不由客户端猜测。

### 3.4 通知没有用户控制

- App 连接成功后立即请求通知权限，没有解释价值；
- 注册失败被静默忽略；
- 没有启用/停用、测试通知和状态入口；
- 只监听运行期点击，冷启动通知导航不完整。

目标：在首次创建后台任务时解释并请求通知权限；设置页显示状态并允许控制；冷启动和
运行期点击统一导航到 Task 或具体执行记录。

### 3.5 相机与媒体权限缺少恢复路径

- 永久拒绝相机/麦克风后仍只重复请求权限，没有“打开系统设置”；
- 拍照和录音异常无明确提示；
- 拍照后没有预览/重拍，直接返回对话。

目标：区分首次请求与永久拒绝；提供设置入口；拍照后允许“使用照片/重拍”。

## 4. P2：信息架构与可理解性

### 4.1 “状态”页更像开发者诊断页

当前直接展示 Token 数、内部 extension ID、effect/risk 和审计代码。普通用户最关心的是：

- 小诺是否在线；
- 当前模型是否可用；
- 电脑控制、网络、文件等能力是否可用；
- 哪些能力执行前需要确认；
- 出问题时如何恢复。

目标：默认展示可理解的健康状态和解决动作；原始工具、Token 与审计日志放入“高级诊断”。

### 4.2 主导航拥挤

对话页顶部同时放置新话题、任务、状态、版本，点击区域小且更新入口重复。

目标：一级导航只保留“对话”和“任务”；新话题属于对话操作；连接、通知、能力和版本进入
统一设置/状态页。发现更新时使用一次全局提示。

### 4.3 无障碍与破坏性操作不一致

多数图标按钮、附件删除、任务控制没有完整无障碍标签；删除、停止、切换话题等操作缺少
一致的确认规则。

目标：所有图标和状态具备可读标签；危险操作使用统一确认组件；按钮在处理中显示明确状态
并防止重复提交。

## 5. 实施顺序

1. 让当前实现回归既有 Task / TaskExecution / ExecutionAttempt 正向设计，并重构对应 API；
2. 修复连接身份原子存储、重新配对和事件游标隔离；
3. 补齐对话停止、重试、错误恢复和会话历史；
4. 统一 Artifact、Approval 和通知闭环；
5. 重做状态/设置页和全局更新策略；
6. 完成无障碍、加载/空态/错误态和破坏性操作一致性检查。
