# 小诺个人助手产品改进计划

> 版本：v1.0
> 日期：2026-08-22
> 范围：Android App、Node、Core、Hub、Relay、mDNS/P2P、Agent/Codex、任务、审批、Artifact、Console、飞书和钉钉入口
> 目标：让用户只需要提出目标，系统负责执行、恢复、交付结果；只有需要人类决定时通知人类。

## 1. 产品目标

小诺不是聊天 Demo，也不是把电脑能力堆在一个界面里。产品最终应形成下面的闭环：

```text
用户提出目标
  -> 系统理解目标并给出执行方式
  -> 执行前检查能力、权限和副作用
  -> 自动完成安全且可验证的步骤
  -> 需要决定时暂停并通知用户
  -> 断线、重启或关闭 App 后继续运行
  -> 交付结果、文件、证据和下一步
```

### 1.1 用户承诺

- 用户不需要理解 Node、Agent、Provider、Transport、Session、Attempt 等内部对象。
- 用户不需要一直保持 App 打开，后台任务仍可运行并在关键状态发生时通知。
- 任何失败都必须说明发生了什么、是否产生副作用以及下一步如何恢复。
- 自动化优先，但高风险和不可验证的外部副作用必须保持安全确认。
- mDNS、P2P、Relay 由系统自动选择，不让用户手动管理连接技术。

### 1.2 非目标

本计划不建设企业管理功能，包括 Fleet、组织级权限、企业成本统计、团队治理、复杂审计中心和企业运维报表。
本阶段优先服务一个人远程指挥自己的电脑和个人工作流。

## 2. 当前基线

### 2.1 已有能力

- 本机文件、Shell、桌面、截图、窗口和剪贴板操作。
- Knoa Agent、Codex Runtime、多 Provider、本地 llama.cpp 和视觉模型。
- Conversation、Task、TaskExecution、Approval、Interaction、Artifact 和失败副作用提示。
- 一次性、定时、周期和事件触发任务。
- App、CLI、TUI、飞书、钉钉等入口。
- Hub、Workspace、Node、Relay、P2P、mDNS 和断线恢复。
- 附件上传、下载、预览、保存、分享及任务结果交付。
- Console 健康检查、连接诊断和文本化状态标签。

### 2.2 当前主要断点

1. 首次使用仍暴露 Workspace、Node、Agent、Model 等内部概念。
2. Hub 请求缺少统一超时和取消，部分页面可能长时间转圈。
3. App 提醒主要依赖运行时事件，没有形成可靠的系统级后台通知。
4. 重新配对可能保留旧 Core Session 和 event cursor，存在状态串线风险。
5. Chat、Task、Execution、Result、Artifact 仍是分散页面，不是统一工作时间线。
6. Workspace 缓存没有 TTL、更新时间和清晰的离线状态。
7. mDNS Node 端正常，但 App 发现失败时缺少面向用户的解释和恢复动作。
8. Console 诊断信息丰富，但仍偏开发者视角，一键修复不足。
9. Codex、视觉模型和 MCP 的配置错误仍可能以内部路径或运行时错误呈现。
10. Windows 更新、服务重启和版本来源曾出现不一致，需要持续做幂等和版本校验。

## 3. 正向架构原则

### 3.1 保留领域所有权

- Core 拥有 Conversation、Task、Approval、Artifact 和持久事件。
- Gateway 和 Channel 只负责认证、协议适配和展示，不复制业务判断。
- Agent Runtime 通过稳定 SPI 接入 Knoa、Codex 和其他执行器。
- Capability Gateway 是工具和 MCP 副作用的统一检查点。
- Hub 负责身份、Workspace、Node 目录、授权资源和 Relay。
- Lifecycle 只负责服务、安装、更新和恢复，不进入业务领域。

### 3.2 新增而不重复的收敛层

#### User Work Facade

面向 App、飞书、钉钉和 CLI 提供统一的工作摘要，不合并内部数据库模型：

- 用户目标和标题；
- 当前状态和阶段；
- 进度与最近活动；
- 是否需要用户决定；
- 结果、文件和证据；
- 恢复、重试、继续和取消动作。

#### Unified User Status

Conversation Turn 和 Task Execution 对外统一映射为：

```text
准备中、执行中、等待确认、已完成、部分完成、失败、已暂停、需要恢复
```

状态必须由服务端持久事实提供，客户端不得依赖事件到达顺序自行猜测。

#### Notification Intent

Core 产生持久化通知事实，渠道负责渲染：

```text
任务完成、任务失败、等待审批、等待补充信息、Node 离线、需要重新配对、需要更新
```

不得为 App、飞书、钉钉分别建立第二套业务通知状态。

#### Capability Preflight

执行前统一检查 Node、目录、Runtime、模型、MCP 凭据、权限和副作用；检查结果必须包含用户可理解的原因和恢复动作。

#### Async UI State

移动端所有页面统一使用 loading、ready、empty、offline、error、retrying 状态组件。

## 4. 分阶段实施计划

### Phase 0：版本、部署和可观测性基线

目标：先保证用户拿到的版本、实际运行版本和服务状态一致。

工作项：

- 所有产品版本由单一来源生成，Wheel、Node API、Console、App 更新检查统一读取。
- 更新前执行端口、旧服务和进程树预检；确认释放后再启动。
- Windows/Linux 更新脚本幂等，失败时停止无意义的重启循环。
- 更新完成后校验 commit、运行版本、端口和健康接口。
- 日志统一记录启动、停止、重启、传输切换和版本信息。
- Console 显示“安装版本”和“实际运行版本”，不允许二者静默不一致。

验收：

- 连续执行两次更新不会产生孤儿进程或端口占用。
- 服务启动失败时 30 秒内显示根因和恢复动作，不进入无限重启。
- 安装包版本、Node 返回版本和 Console 版本完全一致。

### Phase 1：首次使用和连接闭环

目标：用户不理解内部架构也能完成第一次真实工作。

工作项：

- 将 Account、Workspace、Node、Agent 的首次流程包装成“连接电脑”。
- 配对完成后自动执行能力检查并给出可执行的第一步。
- 首屏默认提供目标输入，而不是技术对象列表。
- mDNS 发现增加超时、重试、局域网检查和清晰原因。
- Relay/P2P/mDNS 只在高级诊断中展示，普通页面显示“本地连接/远程连接/自动连接”。
- 所有 Hub 请求增加 AbortController、连接超时和可重试错误分类。
- Splash、Workspace、Node 页面必须存在离线、失败、重试和返回路径。

验收：

- 新用户五分钟内完成一次真实文件、代码或资料任务。
- 任意网络故障不会导致永久转圈。
- mDNS 未发现时，用户能看到是“尚未查询、局域网不可达、发现超时还是连接失败”。

### Phase 2：统一工作体验

目标：用户只面对“工作”，不需要选择内部执行对象。

工作项：

- 引入 User Work Facade 只读摘要 API。
- Chat、Task、Execution、Result、Artifact 合并为统一 Work Detail 视图。
- 目标输入自动建议即时、后台或周期执行方式。
- 任务详情显示目标、状态、进度、审批、结果和恢复动作。
- 重试、取消、继续和重新执行必须明确是否可能产生重复副作用。
- 同一工作在 App、飞书、钉钉和 CLI 显示同一终态。

验收：

- 用户无需先判断“新会话还是新任务”。
- 一个工作完成后，在同一详情中找到摘要、文件、证据和再次执行入口。
- 重试不产生重复工作或重复外部副作用。

### Phase 3：后台自动化和可靠通知

目标：App 关闭、手机断网或用户离开后，任务仍然可靠运行并在关键状态通知用户。

工作项：

- Core 持久化 Notification Intent。
- App 增加系统级通知注册、状态页、测试通知和冷启动导航。
- 飞书、钉钉和桌面通知使用同一通知事实。
- 通知内容包含原因、影响、选项、截止时间和打开后的目标工作。
- 任务完成、失败、等待审批、等待输入、Node 离线均可通知。
- 只自动重试安全、幂等、可验证的步骤；未知副作用必须暂停并通知。

验收：

- App 完全关闭时，后台任务仍能在完成或需要决定时通知用户。
- 点击通知直接进入对应 Work Detail 或 Approval。
- 同一事件不会重复通知，也不会因事件重放漏通知。

### Phase 4：能力预检和结果可信度

目标：尽量在执行前发现问题，执行后提供足够证据让用户相信结果。

工作项：

- Codex、llama.cpp、Vision、MCP、目录和凭据统一预检。
- 预检结果使用用户语言，并提供自动修复或明确的下一步。
- Vision 冷启动、空 observation 和重试显示进度，不暴露内部 call_id。
- 结果页聚合摘要、产物、证据、部分失败和副作用状态。
- 生成文件提供保存、分享、再次打开和再次执行入口。

验收：

- 能在执行前发现常见 Runtime、目录、模型和权限问题。
- 图片首次分析失败时用户知道系统正在重试。
- 结果页面能回答“做了什么、改了什么、生成了什么、是否需要我确认”。

### Phase 5：个人能力产品化

目标：以少量高价值 Skill 体现实际能力，不继续堆积底层技术名词。

首批 Skill：

- 文件整理和归档；
- 图片整理和分类；
- 代码问题定位、修改和测试；
- 文档总结和结构化提取；
- 下载目录清理；
- 定时个人报告；
- 本机资料搜索和结果交付。

每个 Skill 必须包含：目标示例、能力预检、风险说明、执行进度、产物和恢复方式。

## 5. 数据和身份隔离要求

- 重新配对或切换 Node 时原子清理 Session Token、Core Session、Event Cursor 和连接恢复状态。
- 账户切换时清理不属于当前账户的缓存、未读提醒和本地事件断点。
- Workspace 缓存增加 TTL、更新时间、版本和主动刷新接口。
- 任务状态以服务端持久事实为准，客户端不通过事件顺序推导终态。
- 高风险工具和 MCP 写操作继续 fail-closed。

## 6. 验收指标

### 用户体验

- 首次连接到第一次真实结果不超过 5 分钟。
- 任何页面不因网络或服务错误永久显示加载动画。
- 普通用户不需要理解 Node、Agent、Transport 和 Runtime。
- 每个失败状态都有原因、影响和可执行恢复动作。

### 可靠性

- App、飞书、钉钉、CLI 对同一工作显示一致状态。
- App 关闭后后台任务继续运行。
- 网络切换、Node 重启和 Relay/P2P/mDNS 切换不会重复执行副作用。
- 更新失败不会留下孤儿服务、端口占用或无限重启。

### 结果和信任

- 每个完成任务都有摘要、产物、证据和再次执行入口。
- 高风险动作在执行前展示影响范围、可撤销性和关键参数。
- 未知副作用不自动重放，必须暂停并通知用户。

## 7. 发布门禁

每个阶段发布前必须完成：

1. Python 测试和移动端测试；
2. 移动端类型检查；
3. Node Console 健康检查；
4. Windows/Linux 服务停止、启动、更新和回滚验证；
5. 版本、commit、安装包和运行时一致性验证；
6. mDNS、P2P、Relay 至少一条真实连接链路验证；
7. App 断网、恢复、冷启动和缓存场景验证；
8. 飞书/钉钉通知和文件交付验证；
9. 高风险操作审批和重复执行防护验证。

## 8. 当前执行顺序

```text
Phase 0 版本与部署基线
  -> Phase 1 首次使用与连接闭环
  -> Phase 2 统一工作体验
  -> Phase 3 后台通知与自动化
  -> Phase 4 能力预检与结果可信度
  -> Phase 5 个人 Skill 产品化
```

每个阶段可以独立提交和发布，但不得在发布前跳过测试、版本一致性和真实设备验证。
