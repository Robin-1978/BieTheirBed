# 小诺产品功能审查（2026-08-23）

## 结论先行

小诺已经具备“能在用户电脑上执行工作的运行基础”，不是只有聊天界面的 Demo：Node 可以调用本地文件、Shell、桌面控制、截图、图片理解、本地模型、记忆、通知、任务和 MCP；Core 具备持久任务、审批、重试、取消、定时/事件触发、Artifact 和重启恢复；App 可以远程选择电脑、创建任务、查看结果并接收在线提醒。

但是，从用户视角还不能稳定地称为“全方位个人助手/虚拟员工”。目前最主要的断点不在工具数量，而在工作闭环：用户说出目标后，系统还经常要求用户理解 Node、Agent、MCP、Runtime 等内部概念；后台任务在 App 完全关闭时没有可靠的移动端远程推送；任务模板与附件/文件夹输入没有连通；浏览器工作没有产品化入口；结果交付没有统一说明“完成了什么、没有完成什么、产生了什么、下一步是什么”。

综合评分（以个人用户实际完成工作为标准）：

| 维度 | 当前判断 | 说明 |
| --- | --- | --- |
| 本机执行能力 | 强 | 文件、Shell、桌面、视觉、本地模型、MCP 基础齐全 |
| 长任务与恢复 | 强 | Durable Task、Execution、审批、幂等、暂停/继续/重试和重启恢复已存在 |
| 多电脑与连接 | 中上 | mDNS、P2P、Relay 和节点选择存在，但链路竞速、耗时可观测性和导航等待仍需收敛 |
| 结果交付 | 中 | Artifact 和分享存在，但缺少统一工作摘要和证据/变更说明 |
| 移动端易用性 | 中 | 页面覆盖广、缓存和离线队列已有，但内部概念多、入口分散、部分页面仍等待网络 |
| 后台通知 | 弱到中 | 当前主要是 App 在线事件流加本地通知；App 关闭时的远程推送闭环未见实现 |
| 浏览器工作 | 弱 | 有搜索/抓取和桌面鼠标键盘，但没有稳定的浏览器导航、DOM、会话和下载产品能力 |
| 能力扩展 | 中 | Skill/MCP 可导入和预检，但流程工程化，没有一键能力包 |
| 自我进化 | 初级 | 有评测和候选设计，尚无用户反馈到灰度、监控、回滚的完整控制面 |

## 用户目标链路审查

理想链路应是：

```text
描述目标 → 选择/接受执行电脑 → 自动预检 → 即时执行或后台执行
        → 需要时审批 → 断线/重启后继续 → 结果和文件交付
        → 完成/失败/需决定时通知 → 用户继续、分享或撤销
```

当前每一段的状态：

| 环节 | 当前能力 | 主要断点 | 优先级 |
| --- | --- | --- | --- |
| 描述目标 | Chat 和 Task 新建均可输入目标 | 用户要在“会话”和“任务”之间做内部判断 | P1 |
| 选择电脑 | Task 新建页支持选择 Node，并已显示友好电脑名 | Workspace 的“让小诺做事”入口需要明确执行电脑归属 | P1 |
| 自动预检 | Console 有 Node、端口、mDNS、Relay、llama.cpp、Codex 检查 | 预检结果还没有统一成为任务开始前的用户动作 | P0 |
| 即时/后台执行 | 对话、Durable Task、定时、Webhook、MCP Resource 均存在 | 模板多为 Prompt 预填充，不是结构化能力包 | P1 |
| 审批 | 后端 Approval 和恢复存在 | App 端要把影响范围、可撤销性和下一步说清楚 | P1 |
| 断线/重启恢复 | 任务幂等、重试和恢复基础较强 | App 导航和状态同步仍可能等待连接；移动端后台通知不足 | P0/P1 |
| 结果交付 | Artifact、结果页、分享存在 | 缺少统一完成摘要、改动清单、证据和未完成项 | P0 |
| 通知 | App 在线时可通过事件流生成本地通知；飞书/钉钉有渠道 watcher | 没有确认 App 完全关闭后的系统级远程推送 | P0 |
| 继续/撤销 | 任务支持暂停、继续、取消、重试、重新执行 | 普通用户看不到统一的恢复入口和副作用提示 | P1 |

## 已有实际能力盘点

### 本机和桌面

`src/knoa_platform/tools` 已提供 `read_file`、`write_file`、`run_command`、`read_artifact`、`attach`、`image_inspect`、`clipboard`、`screenshot`、`window`、`mouse`、`hotkey`、`press_key`、`type_text`、`notify` 等工具。Windows Desktop Companion 通过认证 named pipe 让 Session-0 的 Node 控制当前用户桌面。这足以支持文件维护、代码维护、系统检查、截图取证和部分 GUI 操作。

### 研究和资料

已有 `web_search` 与 `web_fetch`，并可通过本地文件、Artifact 和图片理解处理资料。当前更像工具集合，尚未形成“收集来源—抽取—比较—生成 Markdown/PDF/表格—交付”的一键工作能力。

### 长任务和自动化

`src/knoa_platform/automation/service.py`、`repository.py`、`trigger_service.py` 以及 `product_task_lifecycle.py` 提供 Durable Task、Execution、Schedule、Trigger、Approval、Artifact、事件游标、幂等、暂停/继续/取消/重试和重启恢复。能力基础是产品级的，主要缺口是 App 没有把它收敛成“我的工作”视图。

### Jira、GitLab、飞书和钉钉

扩展和渠道可以接入 Jira/GitLab、飞书、钉钉；它们应被定位为个人工作连接器，而不是企业治理中心。当前连接能力存在，但用户仍需要理解 MCP/Server/资源等内部对象，缺少“连接后我能让小诺做什么”的能力说明和模板。

### 模型和视觉

llama.cpp、本地模型共享、Vision 和图片 Artifact 已有。`image_inspect` 仍需要统一处理空 observation、上下文上限和失败重试；产品必须显示“图片是否已上传、模型是否支持视觉、失败是否已重试”，而不是只显示内部错误。

## App 页面逐项审查

| 页面/入口 | 用户目的 | 当前情况 | 结论 |
| --- | --- | --- | --- |
| 首页/帐号/登录 | 进入个人空间 | 基础登录和账户入口存在 | 保留，首屏应直接引导连接电脑和提出目标 |
| Workspace 首页 | 查看空间和开始工作 | 有 Work、Nodes、Members、Resources | 信息架构偏管理面；“让小诺做事”必须明确执行电脑 |
| Work | 查看正在做的工作 | 有工作投影组件 | 需要统一覆盖会话、任务、审批、结果，而不是多套列表 |
| Nodes | 查看可用电脑 | 已改为友好电脑名称，原始 ID 仅高级诊断 | 方向正确；还需显示“能做什么”和当前实际链路 |
| Node 首页 | 管理某台电脑 | 有能力、模型、任务、诊断和设置 | 不应因连接握手阻塞导航；默认隐藏端口、PID、Runtime 等术语 |
| Chat | 即时指挥 | 支持会话、附件、流式回复 | 需要历史缓存、停止/重试、结果卡片和失败恢复 |
| Conversations | 找回历史 | 有列表入口 | 首次进入和删除仍可能等待网络；需要 stale-while-revalidate 和乐观删除 |
| Tasks | 管理后台工作 | 支持模板、Node、Agent、通知、启动策略 | 模板与输入不匹配；需要附件/图片/文件夹选择和统一工作详情 |
| Task Executions | 查看一次执行 | 后端数据完整 | 普通用户应看进度、影响、结果和恢复动作，Execution/Attempt 仅高级诊断 |
| Results/Artifacts | 使用产物 | 支持结果和分享 | 需要完成摘要、修改清单、证据、未完成项和一键继续 |
| Capabilities | 了解能力 | 可展示能力和连接 | 目前容易变成工具目录，应改为用户目标导向的能力包 |
| Pair/Connect/Capture | 配对、连接、采集 | 基础流程存在 | 需要更清晰的网络失败解释和恢复路径 |
| Extensions | 导入 Skill/MCP | 支持本地/远程导入和 inspect/draft/publish | 工程化门槛过高；需要能力包、文件选择器、预检、版本和回滚 |
| Settings | 配置 Agent/Model/System/Update | 配置项丰富 | 内部概念过多；普通设置与高级诊断应分层 |

## P0：会直接损害“能帮我完成工作”的问题

1. **缓存优先和导航不阻塞。** 会话、Workspace、Node、任务、结果均应先读本地快照，再后台刷新。删除、归档、重命名和发送采用乐观更新与可恢复队列。缓存必须按账户、Workspace、Node、Session 隔离，并提供按类别和一键清除，不得删除服务端数据或运行中任务。
2. **统一连接竞速。** mDNS、P2P、Relay 并行探测；首个可用链路承载请求，后续按 `mDNS > P2P > Relay` 升级。所有业务请求记录实际承载链路和阶段耗时，副作用请求不得因切链路重复发送。
3. **执行前预检和可恢复错误。** Codex、llama.cpp、Vision、目录、权限、MCP 和桌面 Companion 在执行前给出用户语言的检查结果；失败必须说明原因、影响、自动修复和重试动作，不能永久转圈。
4. **统一结果交付。** 每项工作都必须回答：完成了什么、没有完成什么、生成/修改了什么、证据在哪里、下一步是什么。结果应能打开、下载、分享、继续执行或撤销。
5. **通知语义不能夸大。** 当前 App 代码（`TaskReminderProvider.tsx` 和 `taskNotifications.ts`）依赖事件流并在本地生成通知；应明确区分“App 在线本地通知”和“App 关闭仍可达的远程推送”。在远程推送真正接通前，不得对用户承诺后台手机通知一定到达。

## P1：决定产品是否好用

1. 统一 User Work 视图，隐藏 Conversation、Task、Execution 的内部差异。
2. 任务新建增加附件、图片、PDF 和文件夹选择；模板从 Prompt 预填充升级为结构化输入和能力包。
3. 提供个人工作能力包：整理电脑、维护项目、图片/资料处理、持续监控、个人报告、远程操作电脑，并显示权限、风险、预计耗时和结果格式。
4. 扩展导入改为“一键安装能力”：导入包、预检权限、展示工具、启用/停用、更新和回滚，默认不要求用户填写 server id 或内部路径。
5. 建立 Webhook/MCP Resource 的用户流程：创建、复制地址、生成密钥、测试触发、暂停和查看最近事件。
6. 浏览器能力产品化。至少提供浏览器启动、导航、页面读取、点击/输入、下载跟踪和持久会话；在实现前不要暗示系统能稳定处理所有网页工作。
7. 后台通知使用统一 Notification Intent；App、桌面、飞书、钉钉复用同一事实，支持去重、深链、测试和过期。
8. 结果、审批和恢复动作统一组件化，显示副作用、可撤销性和重复执行风险。

## P2：形成长期产品壁垒

1. 反馈—失败分类—评测集—候选改进—沙箱回放—人工批准—灰度—监控—回滚的自我进化闭环。
2. 能力包市场和版本治理，但不引入不必要的企业治理中心或通用 Workflow DSL。
3. 浏览器持久化会话、跨渠道工作上下文、主动预取和更细的链路质量评分。
4. Console 默认只展示“正常、需要处理、阻塞”三类状态；Node ID、PID、端口、Transport、Runtime、审计 ID 只放高级诊断。

## 验收标准

- 新用户首次配对后 60 秒内能完成一次文件整理、图片理解或项目维护，不需要理解 Node、Agent、MCP、Runtime。
- 有缓存的任意页面约 300ms 内出现可读内容；网络刷新不阻塞导航；所有加载失败都有明确错误和重试。
- App、Node 重启或网络切换后，运行中任务不重复、不丢失，可继续查看和恢复。
- App 完全关闭时，任务完成、失败和审批通知的到达策略有真实可验证的实现或明确降级说明。
- 任意结果都能看到完成项、未完成项、文件/证据和下一步；副作用操作有审批、幂等和恢复路径。
- 普通页面不显示原始 `node_id`；没有电脑名称时显示“未命名电脑”。
- GitLab/Jira/飞书/钉钉作为个人工作连接器可直接产生可交付结果，而不是只显示连接成功。
