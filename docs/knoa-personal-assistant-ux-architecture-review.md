# Knoa 个人电脑助手：用户体验与正向架构审查

> 审查日期：2026-08-22
> 范围：Knoa App、Node、Core、Agent Runtime、Hub、Lifecycle、飞书/其他入口
> 原则：用户目标优先；后台工作必须可持续、可恢复、可通知；正向设计、高内聚、低耦合、KISS、YAGNI。

## 1. 结论先行

Knoa 的基础能力已经超过 Demo：它有本机执行、Agent Runtime、Codex、文件和桌面能力、MCP/Skill、持久
Conversation、持久 Task、审批、Artifact、通知、Hub、Relay、mDNS、P2P 和多入口。

但用户看到的仍然是多个“能力页面”，还不是一个统一的个人执行助手。当前最大的产品问题不是再增加
一个工具，而是让下面这个闭环在任何入口都稳定成立：

```text
告诉小诺目标
  -> 小诺理解并说明计划
  -> 自动执行能自动执行的部分
  -> 只有需要人决定时通知人
  -> 断线、重启、页面关闭后工作仍可追踪
  -> 交付结果、证据和下一步
```

产品北极星：用户只负责给目标、授权关键决策和接收结果；不需要理解 Node、Transport、Agent、Provider、
Generation、Attempt 等内部对象。

## 2. 真实用户旅程审查

### 2.1 首次使用

当前路径是 Account -> Workspace -> Node -> Pair -> Node/Chat。内部边界清晰，但对普通用户仍然需要理解
太多名词，且“连接成功”与“可以开始工作”之间缺少一个明确的第一步。

目标路径：

```text
安装电脑端
  -> 扫码连接
  -> 自动检查电脑能力
  -> 选择一个真实目标模板或直接说目标
  -> 得到第一个结果
```

验收：五分钟内完成一次真实工作；失败时有明确恢复动作，不出现永久转圈。

### 2.2 日常工作

当前对话、任务、工作区、Node 菜单分别可用，但用户要自己决定“即时对话还是后台任务”。产品应该先收集
目标，再根据目标建议“现在完成”或“后台持续完成”，而不是先要求用户理解两种对象。

目标：

- 默认入口是“告诉小诺你要完成什么”；
- 短目标进入 Conversation，长目标/周期目标进入 Task；
- 用户始终看到同一条工作时间线；
- 内部 Session、TaskDefinition、Execution、Attempt 只用于详情和诊断。

### 2.3 远程指挥与自动处理

当前 Task、Schedule、Trigger、Approval 已存在，但用户体验需要明确三种结果：

1. 已自动完成：通知结果和产物；
2. 等待用户决定：通知影响范围、风险和选项；
3. 暂时无法继续：通知已完成的动作、未知副作用和恢复建议。

任何入口断开都不应取消后台 Task。重新打开 App、飞书或 CLI 后，应从持久状态继续查看和控制。

### 2.4 失败和恢复

当前多个页面已经有错误文案和重试，但仍存在页面级异步状态重复实现的问题。统一要求：

```text
加载中：说明正在做什么
失败：说明发生了什么
副作用：说明是否已经执行过动作
恢复：重试 / 编辑重发 / 查看诊断 / 返回
空态：说明下一步能做什么
```

### 2.5 结果交付

Artifact、任务结果、图片预览和分享能力已经存在，但结果页需要把“结果、证据、原始文件、再次执行”
放在同一工作上下文中，而不是让用户在 Chat、Results、Task Execution 之间寻找。

## 3. 当前能力与产品承诺

| 用户目标 | 当前可用能力 | 当前主要摩擦 | 产品化方向 |
| --- | --- | --- | --- |
| 处理本机文件 | 文件、Artifact、模型 | 需要先理解 Node/权限 | 目标输入后自动说明目录和权限 |
| 修复代码/运行测试 | Shell、文件、Codex | Codex 可见性、Runtime 路径、审批解释 | 自动检查 Runtime，失败可修复 |
| 整理图片和资料 | Vision、Artifact、llama.cpp | 模型配置和空 observation 对用户不可见 | 任务前能力预检，失败自动重试 |
| 定时/周期工作 | Task、Schedule、Trigger | 调度概念暴露过多 | 用自然语言确认计划 |
| 业务系统处理 | MCP/远程资源 | 每个系统仍像独立配置工程 | 以 Skill/目标入口包装能力 |
| 远程指挥 | App、Relay、P2P、mDNS、飞书 | 连接诊断仍偏技术 | 默认只显示本地、远程、自动修复 |
| 需要确认的动作 | Durable Approval | 风险、影响范围、可撤销性需统一 | 统一审批卡片和持久状态 |

明确不承诺：完全无人值守的高风险外部副作用。此类动作必须保持 fail-closed，并说明原因。

## 4. 架构审查结论

### 4.1 应保留的边界

- Core 拥有 Conversation、Task、Approval、Artifact 和持久事件；
- Gateway/Channel 只做认证、协议适配和展示，不复制执行逻辑；
- Agent Runtime 通过稳定 SPI 接入 Knoa/Codex；
- Capability Gateway 是所有工具和 MCP 副作用的唯一检查点；
- Hub 只负责身份、Workspace、Node 目录、授权资源和 Relay；
- Lifecycle 只负责固定服务和发布，不进入业务领域。

这些边界符合高内聚、低耦合，不应为了“统一”而拆成更多微服务。

### 4.2 需要正向收敛的边界

1. **User Work Facade**：面向入口的“工作”查询和命令应统一返回用户可理解的摘要；内部 Conversation/Task
   仍由各自 Service 拥有，不合并数据库模型。
2. **Execution State**：Conversation Turn 和 Task Execution 都应通过同一套用户状态映射暴露运行中、等待决定、
   已完成、失败、已暂停和需要恢复；不让 App/飞书自行猜状态。
3. **Notification Intent**：Core 产生“需要通知什么”的持久事实，渠道负责把它渲染成 App Push、飞书消息或
   本地通知；不让渠道从事件顺序推断业务状态。
4. **Capability Preflight**：在开始执行前提供 bounded 预检结果，避免用户执行到一半才发现 Runtime、模型、
   目录或凭据不可用。
5. **Async UI State**：App 页面使用统一的加载、错误、空态和重试组件；页面只负责领域数据和动作。

### 4.3 反模式与 YAGNI 约束

- 不新增通用 Workflow DSL；Task 的 launch policy 已足够表达当前个人场景；
- 不为每个 Agent 增加专用 UI；Agent 只提供能力描述和用户可用性；
- 不把 mDNS/P2P/Relay 变成用户必须选择的设置；
- 不把 Hub、Node、Lifecycle 拆成更多网络服务；
- 不引入第二套通知队列，先收敛现有 Task 事件和 durable 状态；
- 不为历史错误语义继续增加兼容分支，迁移后删除旧公共模型。

## 5. 重构顺序

### P0：工作闭环和状态可信

1. 引入 User Work Facade 的只读摘要模型，统一 App/Channel 的工作卡片；
2. 引入统一用户状态映射和恢复动作；
3. 所有执行前做能力预检，错误必须携带副作用和恢复信息；
4. App 首屏、任务页、会话页使用统一 Async UI State；
5. 断线/重启后工作状态可重放，客户端不靠事件顺序猜测。

### P1：远程指挥和主动执行

1. 目标输入自动建议即时/后台/周期执行；
2. Notification Intent 统一 App、飞书、桌面通知；
3. 审批卡片统一风险、影响、可撤销性和结果；
4. 结果和证据聚合到工作详情；
5. 自动恢复只重试安全、幂等、可验证的步骤，未知副作用必须停下来通知。

### P2：能力产品化

1. 用少量真实 Skill 包装文件整理、代码维护、资料分析、日报汇总；
2. MCP/Provider/Runtime 预检结果进入用户可理解的能力状态；
3. App 提供目标模板和可复制的真实示例；
4. 高级诊断、原始日志和内部标识只在诊断页出现。

## 6. 验收指标

- 首次连接到第一次真实结果不超过 5 分钟；
- 任何页面不因错误永久显示加载动画；
- 后台 Task 在 App/飞书断开后继续运行，重新进入可看到准确状态；
- 需要用户决定时，通知包含原因、影响、选项和截止时间；
- 结果包含摘要、产物、证据和再次执行入口；
- 同一工作不会因重试或链路切换产生重复副作用；
- App、飞书、CLI 对同一工作显示同一终态；
- 新增代码优先进入唯一领域所有者，避免跨层复制业务判断。

## 7. 当前实施切片

本审查之后先实施两个低风险、高收益切片（首批已落地）：

1. App 统一 Async UI State，已覆盖 Workspace、Tasks、Results 和 Task Execution；首屏保留品牌化恢复页，避免把连接恢复误显示成普通数据加载；
2. Core 增加用户状态映射纯函数和测试，已正式进入 Core Snapshot、Gateway OpenAPI 和移动端类型协议，供 Gateway/Channel 共用。

这两个切片不会改变持久化模型，也不会引入新的网络服务，符合正向设计和 YAGNI。
